# Ticketing coverage beyond Ticketmaster: US and South Asian live music

Researched November 7, 2026. Research only; no product, deployment, or spec changes. This extends [01-data-sources.md](01-data-sources.md). Recommendations below are proposals, not adopted architecture decisions. The current overview explicitly limits the rebuild to Ticketmaster; implementation would require a scoped follow-up and spec changes.

The user clarified that South Asian music was an example, not the intended product focus. See [broad multi-source discovery research](2026-11-07-multi-source-concert-discovery.md) for the current recommendation, actual SOMA/Lodge Room probes, scraping feasibility and implementation sequence.

## Recommendation

Aggregate Concert records from several sources, with outbound ticket links. There is no universal public API that queries every ticket seller. A common record format is achievable; universal discovery and unrestricted reuse are not.

For this project's budget, retain Ticketmaster, test JamBase's non-commercial plan for incremental coverage, and prioritize Sulekha plus a small roster of Southern California promoters and venues for the South Asian gap. Seek a permitted feed from the latter sources; their public websites are useful evidence but do not establish API access or republication rights. Ticket Fairy is a documented, no-key API worth testing, but the live probe below did not establish useful Bollywood coverage.

The key distinction is **discovery across a catalog** versus **management of an organizer's own listings**. An API advertised as “public” can still expose only an authenticated account's data. Buying tickets in Concert Scout and comparing seat-level inventory are separate, substantially larger projects; neither is needed to link people to real Concerts.

## Is there a shared way to query these sites?

Not a shared search endpoint. There are reusable formats and integration patterns:

1. **Source REST/GraphQL API or licensed feed.** Best for incremental updates, stable IDs and cancellations. Scope and display rights vary by provider.
2. **Organizer/venue calendar feeds.** Permissioned JSON/CSV, RSS or iCalendar can work independently of who sells tickets. [The Events Calendar](https://dev.theeventscalendar.com/knowledgebase/introduction-to-the-events-calendar-rest-api/) documents a WordPress REST interface, so some venue adapters can share a parser. Each installation remains its own source and permissions boundary.
3. **Schema.org Event / MusicEvent in JSON-LD.** A portable way to extract published facts from permitted pages. [Google's documentation](https://developers.google.com/search/docs/appearance/structured-data/event) shows dates, location, performers, organizer, status and offers. It is a publishing format, not an exhaustive discovery service or a reuse license. Not every site publishes it, and it can be stale or conflict with visible content.
4. **Web search for discovery leads.** Find canonical pages, then verify against the source record. Search snippets and generated summaries should not become Concert facts. Search-engine result APIs sold by third parties are not first-party Google Events APIs and do not grant rights to source content.

Prefer a scheduled import into a shared Concert pool over live browsing of many sellers for each Search. That is a proposed approach, not a measured latency improvement. Set each source's refresh/cache policy from its agreement; do not copy Ticketmaster's cache policy onto other providers.

Expand by measured regional coverage, not by turning on a “global” flag. Preserve local dates and date precision, IANA time zones where known, country, currency and original names. Unknown time is not midnight. Unknown price is not free. Do not convert currencies or normalize ambiguous zone abbreviations without sufficient evidence.

## Live API probe: Ticket Fairy

Two credential-free GETs through the browser fetch tool returned HTTP 200 JSON on the research date:

```text
https://www.ticketfairy.com/api/v1/events/listing?search=bollywood&section_type=upcoming&sort=start_date&order=asc&size=5

https://www.ticketfairy.com/api/v1/events/listing?country=us&state=California&search=bollywood&section_type=upcoming&include=paid_events,free_events&size=5&order=asc&sort=start_date
```

The first response reported `totalCount=2`: “One Park Pass - MOTIONGATE Dubai” (`experience`, Dubai) and “Entertainment Finance Summit” (`conference`, `filmFestival`, `businessEvent`, Los Angeles). The narrowed California request returned the finance summit. Neither establishes a relevant live Concert. This confirms endpoint reachability and illustrates why keyword search needs validation; it does not prove no Bollywood Concerts exist in the platform. Broader Artist, genre and location samples are still needed. Production use should use the deterministic listing records rather than the provider's natural-language answer endpoint, consistent with ADR 0002.

## Proposed next work, in order

1. **Build a Southern California reference set before adding connectors.** Collect 20–30 real upcoming Concerts from named Artists, community auditoriums, promoters and sellers; have the owner supply favorite Artists if available. Separate live singers/bands, tribute performances, DJ parties, devotional/classical music and non-music programs. Audit Ticketmaster against these exact records. Those counts are proposed sample sizes, not completed measurements.
2. **Test JamBase coverage within its included quota.** Compare the same venue/date/Artist records; record added verified Concerts, duplicate overlap, cancellation accuracy, required fields and requests used. Do not assume its data adds the Sulekha or AXS inventory. Test the intended Developer entitlement rather than only the richer trial.
3. **Prepare targeted feed inquiries for Sulekha and local organizers.** Ask about stable IDs, Lineups, language/category, geo filters, presale/general-sale links, changes/deletions, permitted caching, public display, images, attribution and cost. No outreach has been sent. An authorized organizer's CSV/calendar export may be sufficient without a platform-wide deal.
4. **Only then specify one additional source slice.** Add source-qualified IDs, field provenance and last-verified timestamps. Keep one real Concert with multiple ticket offers; preserve seller identity, currency, price basis/fees and primary/resale distinction. Avoid merging same-day matinee/evening performances or conflating doors and showtime. Quarantine unresolved status/time conflicts. A source failure means partial coverage, not proof there are no Concerts.
5. **Validate with meaningful contracts.** Fixtures should exercise missing Artists/time/price, cancellation and rescheduling, duplicate cross-source listings, afterparty names, inconsistent prose, pagination, quota exhaustion and partial failures. Keep source facts out of model-generated output per ADR 0002 and Spotify account data out of model inputs per ADR 0003. Review [testing boundaries](../development/testing.md) when implementing.

The most useful first addition will be whichever permitted source recovers the family's missing Concerts. A broad feed is easier to integrate, but its relevance must be demonstrated. Comprehensive US or global coverage remains unproven; this research maps viable routes and specific access gaps rather than promising completeness.
